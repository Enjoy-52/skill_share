# summary-work · 工作总结

简要指令：`summary-work`（等同于「总结工作 / 工作日报 / 工作日志 / 今日总结 / 工作复盘」）。

将当前会话与仓库中的**真实进展**整理为五段式工作报告。读完本 Skill 后先收集证据再输出，不要先追问无关细节。

## 工作流

1. **确定范围**
   - 默认：当前对话上下文 + 今日（本地时区）git 活动
   - 用户指定日期/里程碑/分支时，按指定范围执行

2. **收集证据**（按需并行，缺什么查什么）
   - 对话历史：用户目标、已做决策、未完成项
   - Git：`git log`、`git status`、子模块提交；父仓与子模块分别查看
   - 变更面：`git diff --stat`、关键文件/文档（doc、README、部署配置）
   - 未提交改动：区分「已完成但未提交」与「进行中」

3. **归类填槽**
   - 目标：从需求/里程碑/文档/对话提炼，写「要达成什么」
   - 已完成工作：可验证的交付（代码、部署、文档、测试），动词开头、编号罗列
   - 解决的问题：问题 → 处理方式（表格或编号）
   - 剩余问题：未验收、阻塞、待配置、已知风险；无则写「暂无」
   - 总结：1–3 句概括进展、价值与下一步重心

4. **输出**
   - 默认只输出下方五段模板（可复制块）
   - 用户要求日报/邮件/Notion 时再调整外层标题，**五段标题不得改动**

## 输出模板（必须原样使用这些标题）

```text
【目标】
1. 
2. 

【已完成工作】
1. 
2. 

【解决的问题】
1. 
2. 

【剩余问题】
1. 
2. 

【总结】

```

## 填写要点

| 段 | 填什么 |
|----|--------|
| 目标 | 当前阶段/今日要达成的业务或技术目标；可含里程碑编号（如 V1.1 Phase C） |
| 已完成工作 | 已落地且可指证的项：功能、修复、文档、部署、提交；每项一行，动词开头 |
| 解决的问题 | 遇到的障碍及已采取的处理；可用「问题 → 处理」 |
| 剩余问题 | 未闭环项、待验证、依赖外部、技术债；确实没有则写「暂无。」 |
| 总结 | 整体进展评价 + 下一步建议（1–3 句，不重复上文细节） |

## 质量门禁

- 五段标题一字不改；空段不允许整段省略（无内容写「暂无。」或「待补充：…」）。
- 各段用编号列表；已完成工作与剩余问题各至少 1 条，除非明确无项。
- **不得编造未见过的提交、功能、问题或数据**；证据不足时用「待补充：…」占位。
- 不把推测写成事实；未提交改动标注「本地未提交」。
- 含子模块时，在已完成工作中注明父仓/子模块归属（如 src、deploy）。
- 用户要求中文则全文中文；保持简洁，避免堆砌 commit hash。

## 证据优先级

1. 用户明确陈述的目标与结论
2. 当前会话中的实现与验证结果
3. Git 提交记录与 diff
4. 项目文档（doc、README、方案）
5. 禁止仅凭旧记忆或猜测填充

## 示例（结构示意）

```text
【目标】
1. 打通 V1.1 推送闭环，满足高相关公告触达与可观测。
2. 推进 P0 省扩源，消除已启用源无 adapter 导致的调度失败。

【已完成工作】
1. 新增 PortalAdapter，修复 jsccgp、zjggzy 等源调度 KeyError。
2. 生产 compose 补齐 scheduler、crawler-worker、push-worker 四服务栈。
3. push-worker 消费 tender.high 事件并写入 push_records；管理后台新增推送记录 Tab。
4. 编写 doc22 扩源清单与 doc23 推送部署方案。

【解决的问题】
1. 已启用源无 adapter → 通用 PortalAdapter + registry 回退。
2. 容器内找不到 sources.json → APP_ROOT 与向上查找 config。

【剩余问题】
1. 209 生产全链路（高相关触达、日报 Cron）待验收。
2. P0 省按探针评分灰度启用尚未执行。

【总结】
今日完成扩源适配与 V1.1 推送主链路，生产部署骨架已就绪。下一步聚焦生产验证与 P0 灰度启用。
```
