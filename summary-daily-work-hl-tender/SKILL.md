# summary-daily-work-hl-tender · hl-tender 工作日报

简要指令：`summary-daily-work-hl-tender`（等同于「hl-tender 工作日报 / 写入日报文件夹」）。

将 **hl-tender** 仓库当日真实进展整理为六段式日报，写入固定目录。先收集证据再输出，不要先追问无关细节。

## 输出目录与命名

| 项 | 值 |
|----|-----|
| 目录 | `e:\Company\HeilanSC-总部\能碳数智技术中心\月度绩效\软件组\日报填写\2026年` |
| 文件名 | `工作日报-2026.M.D.txt`（月/日不补零，如 `工作日报-2026.7.24.txt`） |
| 编码 | UTF-8 |
| 参考样例 | 同目录下已有 `工作日报-2026.7.22.txt`、`工作日报-2026.7.23.txt` |

**用户未指定日期时**：按本地时区「今日」生成并写入对应文件；若文件已存在，覆盖更新。

## 工作流

1. **读参考样例**（同目录最新一份 `.txt`），对齐段落结构与 IT 工程师行文风格。
2. **收集证据**（并行）：
   - 当前对话：目标、决策、验收结论
   - 父仓：`git log --since=今日`、`git status`、`git diff --stat`
   - 子模块 `deploy/`、`src/`：同上
   - 项目文档：`doc/15`、`doc/22` 等当日变更
3. **归类填槽**（六段模板，见下）。
4. **写入文件**到输出目录，并向用户回报完整路径。

## 输出模板（标题一字不改）

```text
【目标】
1. 
2. 

【已完成工作】
1. 
2. 

【解决的问题】
1. 
2. 

【剩余问题】
1. 
2. 

【总结】

【下一步建议】
```

## 行文风格（IT 工程师）

- 简体中文；动词开头、编号罗列；简洁可验证，不堆 commit hash。
- **已完成工作**：写交付物（功能/修复/文档/脚本/部署/验收数据）；子模块改动标注 `子模块 src/` 或 `子模块 deploy/`。
- **解决的问题**：`问题 → 处理` 格式。
- **剩余问题**：未验收、未部署、探针未达标、文档漂移等；无则写「暂无。」
- **总结**：1–2 句评价与价值，不写行动项。
- **下一步建议**：1 段或编号，承接剩余问题；可含 209 部署、复探、24h 观察等运维动作。
- 路径/表名/API 用反引号；避免「Loop」「Agent」等非汇报用语，改用「按计划推进」「集中开发」等。

## 填写要点

| 段 | 填什么 |
|----|--------|
| 目标 | 当日业务/技术目标；里程碑如 V1.1、批次 B、209 验收 |
| 已完成工作 | 可验证交付；含推送、发版 Tag、生产验收数据 |
| 解决的问题 | 阻塞与修复措施 |
| 剩余问题 | 未闭环项；本地未提交须标注 |
| 总结 | 进展 + 价值 |
| 下一步建议 | 可执行后续，写清环境（如 209）与顺序 |

## hl-tender 证据清单

优先检索：

- 父仓 `doc/`、`config/`、`scripts/`
- 子模块 `src/`：api、web-admin、push-worker、crawler-adapters、tender_shared
- 子模块 `deploy/`：verify-batch-b.sh、docker-compose.prod.yml
- 进度：`src/dev/progress.json`、`doc/15-V1.1功能完善分析与研发任务清单.md`
- 扩源：`doc/22-P0扩源落地执行清单.md`

## 质量门禁

- 六段标题不得改动；每段至少 1 条（明确无项写「暂无。」）。
- **不得编造**未见过的提交、验收数据、源 ID、条数。
- 未提交改动标注「本地未提交」。
- 写入前确认目标日期与文件名一致。

## 与 summary-daily-work 的关系

- `summary-daily-work`：通用六段模板，默认仅输出可复制文本块。
- **本 Skill**：专用于 hl-tender，**必须写入**上述绩效日报目录，并按已有 `.txt` 样例的行文风格输出。
